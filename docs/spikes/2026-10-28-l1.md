# L1: Astro facts, locally

Run on 2026-10-28 with Astro 7.4.2 and Node 26. The app is in [`2026-10-28-l1/app/`](2026-10-28-l1/app/), in its final configuration; `src/assets/pic.png` is any small PNG and is left out. A minimal adapter in `astro.config.mjs` logs the hooks, and `server.mjs` calls `createApp()` and `app.render()`. Each step changed one thing, as described below.

## 1. A prerendered site with one `server:defer` island

Two prerendered pages, one with `<Island server:defer />`, and a control build without the island.

- `buildOutput` in `astro:config:done`, read before `setAdapter`, is `"static"` in both builds.
- `astro:routes:resolved` runs before `astro:config:done`, and again after it. Both builds list the same routes, including the internal `/_server-islands/[name]`, so the route list cannot tell them apart.
- The difference is in the output. With the island, Astro still builds a server entry (`entry.mjs`, the island chunk and a server island manifest). Without it, the build holds only HTML.
- That server answers the island URL from the prerendered HTML with 200 and the island's HTML.

So ADR 0003 needs no build failure: in `astro:build:done`, the adapter emits a script when Astro emitted a server entry, whatever `buildOutput` said.

## 2. `staticHeaders` with `security.csp`

Prerendered `/`, `/about` and `/404`, an on-demand `/dynamic`, and `security: { csp: true }`.

- `routeToHeaders` is keyed by pathname: `/`, `/about` and `/404`. On-demand routes are not in it.
- Each entry holds `content-security-policy` and `content-type`. The three pages had two distinct policies, because their inline scripts differ.
- `/404` is in the map, so `404.html` gets its policy as a header too.
- With `staticHeaders: true`, the CSP `<meta>` tag is gone from all three HTML files. With `false`, all three keep it.
- `staticHeaders` is a plain value in `setAdapter`, so it can follow `buildOutput`. But an island site reports `"static"` and still gets a script (step 1), so "only with a script" cannot be decided in `astro:config:done` for that case. Leaving `staticHeaders` off then is safe: the policy stays in the HTML.

## 3. Redirects with `build.redirects: false`

Config redirects: `/old` to `/about`, `/blog/[slug]` to `/posts/[slug]`, `/away` to an external URL, and `/temp` with status 302.

- No HTML file is written for any redirect.
- With `app.match(request, true)`:

  | Request | Response |
  | --- | --- |
  | `GET /old?x=1` | 301 to `/about` |
  | `POST /old` | 308 to `/about` |
  | `GET /blog/hello?x=1` | 301 to `/posts/hello` |
  | `GET /away` | 301 to the external URL |
  | `GET /temp` and `POST /temp` | 302 to `/about` |

- The visitor's query is not kept: `/old?x=1` goes to `/about`, not `/about?x=1`.
- With `app.match(request)` (no second argument), `/old` and `/temp` answer 404, because Astro marks redirects without a parameter as prerendered. The adapter has to call `app.match(request, true)`.

## 4. Sharp

A prerendered page with `<Image>` of a local PNG.

- With Astro's default image service, the image is optimized to WebP at build. But the server output then also holds Astro's Sharp service and the Sharp library itself (322 kB, with `createRequire`, `node:module` and native binding lookups), as a lazy part behind the image endpoint.
- With the 7.4 split, `image.service: { build: { entrypoint: 'astro/assets/services/sharp' }, runtime: { entrypoint: 'astro/assets/services/noop' } }`, the WebP is still generated at build and the Sharp library is absent from the server output.
- So the adapter must set the runtime service to no-op when the project uses Sharp. That is the mechanism ADR 0006 was missing.

## Found along the way

- The server output contains absolute paths of the build machine (the project root and `node_modules` paths in the serialized manifest). They end up in the deployed script. Not checked further: whether Astro offers a way to avoid it.
