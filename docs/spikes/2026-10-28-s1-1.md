# S1.1: loading server parts on bunny.net

Run on 2026-10-28 against a throwaway standalone script, its pull zone and a storage zone in DE, all deleted afterwards. The sources are in [`2026-10-28-s1-1/`](2026-10-28-s1-1/): `rollup.mjs` builds `src/` into `System.register` parts, and `probe.js` is appended to `systemjs@6.15.1` `dist/s.min.js` to form the script.

## Setup

- Rollup 4.65.1 splits four modules into four parts: `entry` imports `a` and `d` dynamically, and both import a shared `b` statically.
- The parts are uploaded under `_bunny/server/` and read through the Storage API with the zone's read-only password, held as a script secret.
- `s.js` gets two hooks: `shouldFetch` returns true, and `fetch` adds the `AccessKey` header and sets `content-type: application/javascript`.
- The script reports `Deno.version` and answers a JSON report per request. Two requests, each with a fresh query string.

## Results

Runtime: Deno 2.7.12, V8 14.7.173.20.

| Probe | Result |
| --- | --- |
| `import()` of a `data:` URL | Fails: "disallowed module reference" |
| `import()` of a `blob:` URL | Fails: "failed to resolve module" |
| `import()` of an `https:` URL (the script's own zone) | Fails: "failed to resolve module" |
| `import()` of a relative specifier | Fails: "disallowed module reference" |
| Indirect `(0, eval)` | Works |
| `new Function` | Works |
| `s.js` loading the chain from the Storage API | Works: four fetches (`entry`, `a`, `d`, `b`), 78 ms and 51 ms from the Netherlands to the DE main region |
| A second `System.import` in the same isolate | Works with no new fetch |
| SHA-256, 0.5 / 3 / 10 MB | 1.0 / 6.3 / 14.8 ms and 2.1 / 4.7 / 15.8 ms |

## What it decides

- `import()` fails in every form tried, so server code cannot be split with native modules. ADR 0007's premise holds.
- `s.js` with indirect `eval` loads a split chain on bunny.net, including a part shared through a static import. The split decision stands, and L2 and M2 can go ahead.
- Hashing a part is cheap next to fetching it: about 15 ms for 10 MB, against tens of milliseconds for a fetch from the same region.
- Each request started in a new isolate and fetched all four parts again, consistent with cold isolates at low traffic. This is why S1 step 3 measures the part transport.
- The Storage API answered `content-type: application/javascript` for a `.js` file uploaded as `application/octet-stream`. This feeds S1 step 6.

## Not covered

- Latency from other regions, the Cache API, and the pull zone alternative: S1 step 3.
- Middleware scripts: the same globals are expected, not checked.
