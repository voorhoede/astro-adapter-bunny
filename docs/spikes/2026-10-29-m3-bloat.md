# M3 bloat: a heavy packed site on bunny.net

Run on 2026-10-29 against throwaway standalone scripts, all deleted afterwards. The questions: where a packed script stops starting, whether a heavy realistic site builds and renders through the adapter, whether a request can fail on subrequests, and how much memory a packed script holds. Runtime locally: Deno 2.9.5, Node 26.10.0, Astro 7.4.2. Every script was packed by the M3 `build/bundle` of the working tree (`bundle.ts` SHA-256 `e88d0f71ad3e...`).

Every number below is **measured** unless it is labeled derived (arithmetic on measured numbers) or expected (not measured). MB is 10^6 bytes; the adapter's own messages print MiB. The scripts and the app are in [`2026-10-29-m3-bloat/`](2026-10-29-m3-bloat/).

## Setup

- The app (`app/`): `output: 'server'`, the adapter as `bunny({ script: 'standalone' })`, MDX. 437 on-demand routes: 300 generated pages, 120 markdown and MDX posts from a content collection, Shiki `<Code>` for 8 languages (`/code/all` renders all 8, the heavy route), 7,638 icons from `@iconify-json/mdi`, i18next with 20 locales of 400 keys, date-fns with locales, lodash-es, zod form validation, marked plus a sanitizer, an endpoint for subrequests.
- A knob, `GEN_MB`, adds generated code: one module per generated page, built from functions with loops, switches, object literals and string literals over a 4,000 word vocabulary, all reachable from the page.
- The same app was built at 10 sizes. `pack.mjs` runs the adapter's `bundle()` on `dist/server` without the integration's 7 MB check, so larger sizes could be deployed.
- Cold detection: a spike middleware puts an isolate id and a per-isolate request count in response headers. Cold is count 1.
- Globalping: 10 cells (5 sizes, `/` and `/code/all`), New York, Frankfurt and Singapore, in two windows between about 22:00 and 22:50 UTC. One window had 1 probe per region, the other 3. Probes served by a PoP outside their region were dropped (47 of 411).

### Derived

- **The packed app starts up to 8,348,612 bytes and stops at 9,563,716.** Between them, publishing fails with a 500, so no packed script in that window can be tested at all.
- **It is not startup time.** A packed script at 8.35 MB answered cold `/` within 19 to 56 ms per MB of the 4.35 MB one (next section), and the scripts that stop do not time out: they answer 400 at once. What stops them is on the platform side: a publish error between about 8.4 and 9.3 MB that depends on content (repeated padding of the same size publishes), and above about 9.4 MB a script that publishes but does not start.
- **Ratio of server output to script:** 4.35 for the app without generated code, 4.11 for the generated code (10.9 MB of server output added 2.65 MB of script). So the app stopped between 36.2 and 42.0 MB of `dist/server`.
- Expected for the reference site (2.74 MB of server bundle without Shiki) at these ratios: 0.63 to 0.67 MB of script. Not measured.

## 2. The heavy site

- **Builds through the adapter** up to the 10 MB size (7,006,568 bytes, under 7 MiB) with one warning: the script is above 1 MB. From 14 MB on, the build fails by design: "The script is 7.5 MB, above the 7 MB bunny.net reliably starts."
- **Every route renders locally with the same HTML as Node**: 437 of 437 routes at every size from 0 to 36 MB, status 200 and the same SHA-256 from the packed script under Deno (`local.mjs`) as from `dist/server/entry.mjs` under Node.
- The eager part was 623,434 bytes at every size; 696 lazy chunks were packed.

### Adapter build problem: `sanitize-html`

- With `sanitize-html` 2.18.1 as the sanitizer, the build passes without an error or warning, but **every route answers 500** under the Deno harness (437 of 437), while Node renders all 437. Not deployed to bunny.net; expected the same there, since the loader gives every chunk the same `https://script.invalid/` URL.
- Cause: its dependency `postcss` is CommonJS and calls `require("fs")`, `require("path")` and `require("url")`. Rolldown turns those into `__require = createRequire(import.meta.url)` in its shared `rolldown-runtime` chunk. Under the packed loader `import.meta.url` is `https://script.invalid/rolldown-runtime_...js`, and `createRequire` throws `ERR_INVALID_ARG_VALUE`. Every page chunk imports that runtime chunk, so one CommonJS dependency used on one page breaks every page.
- The build reports `node:module` among the script's builtins in that case, and nothing else hints at it.
- The spike swapped in `xss` 1.0.17 (CommonJS without builtin requires), which works. `SANITIZER=sanitize-html node gen.mjs` reproduces the failure.

## What this means for ADR 0007

- **The 7 MB fail threshold holds, with about 1.3 MB of measured headroom.** A packed app started at 8,348,612 bytes; nothing between 8.4 and 9.3 MB could be published, and nothing above 9.4 MB started. 8 MiB (8,388,608) would sit 40 kB above the largest script that started and below the smallest random-padded one rejected (8.4 MB), so it is the measured edge with no margin.
- **For packed scripts, the limit is the platform, not startup.** The failure is a publish 500 or an immediate 400, not slow cold starts, so the build check is the only place a user learns about it.
- **The 1 MB warning no longer fits.** The heavy app without generated code is already 4.35 MB and warns on every build, while cold `/` grew by 19 to 56 ms per MB of packed script. A threshold on the eager part (623 kB here) or a much higher one would mean more; which, is for the ADR.
- **The roughly 25 MB of source estimate is conservative.** Measured: 36.2 MB of `dist/server` still started, at a ratio of 4.1 to 4.35.
- **No subrequest guard is needed.** 3,000 sequential and 1,000 parallel fetches in one request all succeeded.
- **New: CommonJS dependencies that require a builtin break every route.** Rolldown's `createRequire(import.meta.url)` throws under the loader's `https://script.invalid/` URLs, and the build does not say so. This needs a decision in M3: a build error, or a loader that supports it.
- **Memory** stays open: locally the heap grows to about 11 MB per MB of script when every route is visited; the limit on bunny.net is not known.
