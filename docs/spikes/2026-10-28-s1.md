# S1 steps 2 to 7 and 10: builtins, part transport, hand-off, request facts, storage, caching on bunny.net

Run on 2026-10-28 against throwaway resources, all deleted afterwards: a storage zone in DE (NY and SG replicas added for the transport comparison), a standalone script with the pull zone `bunny scripts create` made for it, a middleware script on a storage-origin pull zone, and a second storage-origin pull zone with no script for the edge rule. Steps 8 and 9 need the adapter's script types and are not covered. Runtime as in S1.1 and S1 step 2 (Deno 2.7.12). Local measurements are from the Netherlands, which Bunny serves from its DE PoP; multi-region ones come from anonymous Globalping HTTP probes.

The sources are in [`2026-10-28-s1/`](2026-10-28-s1/). `deploy.sh` uploads and publishes through the API and waits until the new code answers. `build.sh` prepends `shared.js` (the Cache API part check and the subrequest count) to `probe-standalone.js` or `probe-middleware.js`. Each step has its own shell script, parametrized by `URL`, `SCRIPT_ID` and storage credentials in the environment; `globalping.mjs` runs one measurement from named locations.

## Setup

- Storage fixtures from `files.mjs`: a 200 kB part under `_bunny/server/`, one small file per extension for step 6, and `pre/page.html` for step 4.
- Both scripts read the Storage API with the zone's read-only password as a script secret, as in S1.1.
- Pull zone settings changed from the defaults: the middleware zone got `CacheControlMaxAgeOverride: -1` and `EnableCacheSlice: false`; the standalone zone got `EnableSmartCache: false` and `DisableCookies: false` for step 7 (step 10 lists its defaults).

## Step 3a: Cache API

`shared.js` opens `caches.open('parts')` or `caches.default`, matches a key on the requesting host, and on a miss fetches the 200 kB part from the Storage API and puts it with `public, max-age=31536000`.

Latency, measured:

| Where | Miss: Storage API fetch | Miss: `put` | Hit: `match` | Hit: read body | Time to first byte, hit |
| --- | --- | --- | --- | --- | --- |
| DE PoP, both script types, named and default cache, 4 requests each | 15 to 102 ms | 14 to 24 ms | 9 to 76 ms | 0.2 to 2 ms | |
| Frankfurt (Globalping) | 18 to 23 ms | 11 to 12 ms | 17 to 37 ms | 0.2 to 1.6 ms | 34 to 65 ms |
| New York | 627 to 677 ms | 5 to 7 ms | 10 to 23 ms | 1.5 to 2 ms | 35 to 47 ms |
| Singapore | 1,210 ms | 8 ms | 16 to 18 ms | 2 ms | 120 to 129 ms |
| Other US PoPs, one miss each | 707 (Washington) to 3,653 ms (Los Angeles); Chicago 3,421, Miami 3,080 | 7 to 47 ms | | | |

Scope, measured:

- **Per PoP, not per region.** A key written at the DE PoP missed at seven other European PoPs (AMS, FR, UK, SE, CZ, ES, IT); the one European probe that hit (Vienna) was served by the DE PoP. A key written at NY missed at eight other North American PoPs. This contradicts the documented "per region".
- Different servers within one PoP share entries (written on one server, hit on another, at DE and NY).
- **It behaves as the pull zone's own cache.** On the middleware zone, once an edge rule blocked `*/_bunny/server/*` without a secret header (step 3b), `match` missed and `put` threw `Unable to cache (...) response downstream error`; after disabling the rule, the old entry hit again. On that zone (`IgnoreQueryStrings: true`) a key differing only in its query string hit the other key's entry.
- A visitor requesting the key URL on the standalone zone got the script, not the cached part (`CDN-Cache: MISS`).

Survival, measured: every entry checked was still there at the last check, 692 s (DE, standalone), 682 s (DE, middleware), 543 s (DE) and 536 s (NY). Longer is not measured (see Not covered).

Subrequests, measured: with 0, 10 or 60 `match` calls or 10 `put` calls first, the same request then made 60 Storage API fetches without a failure, in both types. Without cache calls a request made 400 sequential Storage API fetches, 70 fetches to its own other pull zone and 70 to `www.example.com`, all succeeding. So whether `match` and `put` count cannot be told: the documented 50-subrequest limit was not enforced for sequential fetches in any of these.

## Step 3b: edge rule on a cached object

A `BlockRequest` edge rule with two triggers, both required: URL matches `*/_bunny/server/*`, and request header `x-aab-secret` matches none of the secret value. Same result on the storage-origin zone without a script and on the middleware zone (`edge-rule.sh`):

| Request, in order | Result |
| --- | --- |
| No header | 403 |
| With header, twice | 200 `MISS`, then 200 `HIT` |
| No header, three times | 403 each, no `CDN-Cache` header |
| Wrong header | 403 |
| Another path, no header | 200 |

The block holds on a cache hit. But the URL trigger is case-sensitive and the CDN's storage origin is not:

| Path, no header | Result |
| --- | --- |
| `/_bunny/server/p200k.js?x=1`, `/%5Fbunny/...`, `//_bunny/...`, `/x/../_bunny/...`, `/_bunny/server/./...`, `/_bunny/%73erver/...` | 403 |
| `/_Bunny/server/p200k.js` | **200, the part** |
| `/_bunny//server/p200k.js` | **200, the part** |

The Storage API itself is case-sensitive (`_Bunny/...` and `T/A.CSS` answer 404) and folds `//` to `/`. Through a pull zone, `/T/A.CSS` and `/PAGE.HTML` answer 200, so the CDN's read from storage ignores case.

## Step 4: middleware hand-off

`onOriginRequest` rewrites `/page` and `/alias` to `/pre/page.html`, adding `?__aab_visitor=<path>` and the header `x-aab-visitor`; `onOriginResponse` answers what it sees with `public, max-age=300` and a random id (`handoff.sh`).

| Check | Result |
| --- | --- |
| `request.url` in `onOriginRequest` | `http://storage.bunnycdn.com:9000/<visitor path and query>`, with no zone name in the path |
| What `onOriginResponse` sees | `request.url` is the rewritten URL with the query; the added header is present |
| Storage with the query | Ignores it: 200 with the prefixed file; storage `content-type: text/html`, strong `etag` |
| `/page` twice, then `/alias` twice | `MISS`, `HIT`, then `MISS` with a new id, `HIT`: two cache entries, keyed by the visitor URL |
| `/page?v=2` | `HIT` on `/page`'s entry, since the zone ignores query strings |

## Step 6: Storage API, direct reads

`storage-api.sh` with the read-only password. Files were uploaded as `application/octet-stream`.

| File | `Content-Type` | `ETag` | `Last-Modified` | `Cache-Control` |
| --- | --- | --- | --- | --- |
| `.css` | `text/css` | strong, `"<hex mtime>-<hex size>"` | yes | none |
| `.js` | `application/javascript` | same form | yes | none |
| `.svg` | `image/svg+xml` | same form | yes | none |
| `.webmanifest` | `application/octet-stream` | same form | yes | none |
| `.html` | `text/html` | same form | yes | none |
| no extension | `application/octet-stream` | same form | yes | none |

- `Range: bytes=0-9` answers 206 with `Content-Range`, and `Accept-Ranges: bytes` is sent.
- `If-None-Match` with the `ETag`, with a `W/` prefix too, and `If-Modified-Since` with `Last-Modified` each answer 304.
- A query string is ignored (200, full file).

## Step 7: caching through a pull zone in front of a script

`caching.sh`: client A with cookie `user=a`, then client B with `user=b`, then a client with no cookie, against the standalone zone with `CacheControlMaxAgeOverride: -1`.

| Response | `DisableCookies: false` | `DisableCookies: true` (the default) |
| --- | --- | --- |
| `public, max-age=60`, no cookie (control) | Cached, B and C get A's body | |
| `public, max-age=60` with `Set-Cookie` | Not cached: `MISS` three times; each client gets its own `Set-Cookie` | `Set-Cookie` stripped, response cached, and B and C get A's body |
| `s-maxage=60`, `Vary: cookie` | Cached and served to B and C: Vary is ignored, and the `Vary` header is removed from the response | |
| `private, no-store` with `CDN-Cache-Control: max-age=60` | Not cached | |
| `public, max-age=60` with `CDN-Cache-Control: no-store` | Cached | |

So Bunny does not read `CDN-Cache-Control` in either direction.

- **`bunny scripts create --type middleware`** (CLI 0.19.0) refuses to run with its default linked pull zone: "Middleware scripts cannot have linked pull zones". With `--no-pull-zone` it creates the script only; the pull zone has to be made separately.
- **The pull zone `bunny scripts create --type standalone` makes**, read back from the API: `OriginType: 4`, `EdgeScriptExecutionPhase: 0`, `CacheControlMaxAgeOverride: -1`, `DisableCookies: true`, `EnableSmartCache: true`, `IgnoreQueryStrings: false`, `EnableCacheSlice: false`, `UseStaleWhileUpdating: false`, `CacheErrorResponses: false`, `EnableOriginShield: false`, `EnableQueryStringOrdering: true`, no edge rules. ## What it decides

- **Builtins.** `node:constants` and `node:path/win32` join `child_process`, `vm` and `worker_threads` as imports that break startup; bare `buffer` works. The build's builtin check needs the two new ones.
- **The Cache API is not fast enough on a miss outside the storage main region, and a miss is common.** Entries are per PoP, so every PoP pays its own miss, and a miss reads the main region: 0.6 to 3.7 s per 200 kB part from North America, 1.2 s from Singapore. A cold split request took 2 to 3.9 s outside Europe against 0.12 to 0.21 s for one module. Hits are fine (10 to 40 ms per part), and entries survived at least 692 s. By ADR 0007's rule this fails "fast enough"; whether it fails "cached long enough" is not measured.
- **3b passes, with a condition.** The edge rule blocks a request without the header on a cache hit. But a case variant (`/_Bunny/`) or a doubled slash reaches the part, so the rule alone is not enough. The middleware already sees every miss: `routing` has to treat the reserved prefix case-insensitively and after collapsing slashes, in both types and for every transport, because the CDN's storage origin ignores case. That holds today for middleware too: a visitor's `/_Bunny/server/<part>` would reach storage if `routing` matched `/_bunny/` case-sensitively.
- **The pull zone alternative measures much better on a miss:** 110 to 125 ms from New York and 200 to 530 ms from Singapore with replicas, against 0.6 to 2.3 s from the Storage API; hits are equal to Cache API hits. It needs the edge rule, the secret, and the self-request recognized in `onOriginRequest`, as ADR 0007 lists.
- **If the Cache API stays, for example as a layer in front of the pull zone:** its keys follow the pull zone's settings. Put the part hash in the key path, not the query (query strings are ignored on storage-origin zones), and keep the key path outside any edge-rule-blocked prefix (an edge rule on `_bunny/server/` broke `match` and `put`).
- **Split cost when parts are cached:** about 50 to 100 ms more than one module for 1 MB across four parts, at every region. Expected, not measured apart: most of it is evaluating the parts through the loader, since the four `match` calls together take less.
- **Subrequest guard.** The documented 50-subrequest limit did not apply to sequential fetches (400 succeeded). ADR 0007's guard at 25 stays a budget we choose, not a platform limit we measured.
- **Hand-off (design open question 1).** The query carrier works and has evidence: storage ignores it, `onOriginResponse` sees it, and the cache key is the visitor URL, so two visitor paths mapping to one storage key do not share an entry. The header also arrives in `onOriginResponse`.
- **Standalone.** `request.url` is the public URL, so open question 1 in the research is answered. The CDN strips `Range` and `If-*` and turns HEAD into GET before the script, as for URL origins. Responses stream.
- **Storage.** Direct reads return `ETag`, `Last-Modified`, 206 and 304, so standalone can pass conditional and range headers through, but the CDN strips them before the script. `Content-Type` comes from the extension except `.webmanifest` (and no extension), so `storage` still needs its own extension map.
- **Caching.** A `Set-Cookie` response with `public, max-age` is not cached with `DisableCookies: false`, and is cached with the cookie stripped with `DisableCookies: true`. `Vary: cookie` is ignored, so a page that varies on a cookie must not be cacheable. `CDN-Cache-Control` is not read.
- **Script type.** Bunny keeps the type fixed, not only the deploy tool: the API ignores a change.
