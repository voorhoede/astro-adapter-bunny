# S1 packed: lazy server parts gzip + base64 inside the script, on bunny.net

Run on 2026-10-28 against three throwaway standalone scripts, all deleted afterwards. The question: if the build packs every lazy `System.register` part gzipped and base64 encoded into the one script, and the loader unpacks a part on its first import, how fast is that on bunny.net? It depends on whether bunny.net's startup cost grows with script bytes or with parse work. The app is the transport spike's: a small Astro 7 server app with one Shiki `<Code>` block, built into 314 parts (11.6 MB in all). Runtime on bunny.net: Deno 2.7.12, V8 14.7.173.20.

The sources are in [`2026-10-28-s1-packed/`](2026-10-28-s1-packed/).

## Setup

- `build.mjs` writes three standalone scripts. Each renders with `module.default.fetch(request)` under SystemJS 6.15.1 when the request has `?route=<path>`, answers 404 without it, and answers JSON timings instead of the HTML. `?check=1` reports whether `DecompressionStream('gzip')` exists and gunzips a test string.
  - **Packed** (3,359,667 bytes): SystemJS, the entry and the 690 kB eager part as functions, and the other 312 parts as gzip (level 9) + base64 strings. The instantiate hook decodes with `atob`, gunzips with `DecompressionStream`, and evaluates with indirect `eval`. Nothing is fetched. Measured on `/code` and `/`.
  - **Functions** (3,361,348 bytes): generated top-level functions up to the packed script's size, as in S1 step 2's size ladder, and a handler that does no work. Measures startup alone at equal bytes.
  - **C** (1,861,960 bytes): the transport spike's variant C, the six parts `/code` needs registered as functions. Measured on `/code`.
- `local.mjs` runs a built script locally with a stub `Bunny.v1.serve`.
- `setup.sh` creates one standalone script with a linked pull zone per variant; `deploy.sh` publishes a built script and waits until it answers with the build's marker.
- `gp.mjs` (from the transport spike) runs Globalping rounds, one probe per location per round, each with a fresh query string. Seven rounds per cell. `summarize.mjs` prints medians and ranges, dropping probes served by a PoP outside the region asked for (`POPS=US:NY,DE:DE+BE,SG:SG`).
- `teardown.sh` (from the transport spike) deletes everything with the prefix, reading each name back first, and lists what is left.

Cold means the isolate's first request; warm means a later one on the same isolate. Time to first byte includes the render. "Startup gap" is time to first byte minus the handler's run time: connection, isolate start and script evaluation. All four cells ran one after another within about ten minutes.

## Results

### `DecompressionStream`

Measured: `typeof DecompressionStream` is `function` on bunny.net, and `DecompressionStream('gzip')` gunzipped the test string and every packed part used below. No fallback was needed, so none was measured.

### Cold, time to first byte

Median and range in ms, the median startup gap in brackets, sample count in parentheses. Frankfurt probes were served by the DE PoP, once by BE in three of the four cells. Probes served by another region's PoP (one at TX, two at ES, all in the functions row) are left out.

- Unpacking per `/code` part, median over all cold requests: page part 23 ms (then 9 ms to evaluate), Shiki wasm part 41 ms, theme 9 ms, TypeScript grammar 8 ms. The theme and grammar unpack concurrently, so the sum overstates the wall time a little.
- The eager part took the same in both scripts: 18 ms packed, 19 ms in C (median of the import before rendering).
- Locally (Deno 2.9.5, one run each), `/code` unpacked in 19 ms and the first request took 103 ms packed against 79 ms for C. bunny.net unpacked 3 to 5 times slower.

### Warm

Measured: 9 to 30 ms to first byte and 1 to 4 ms in the handler on a warm isolate (13 requests across all variants), with one Frankfurt request to C at 73 ms. A warm request never unpacks: the loader keeps the evaluated module.

### Derived

- **Startup tracks parse work, not bytes.** At equal size, the packed script's startup gap was 106 / 203 / 155 ms against 483 / 598 / 537 ms for generated functions: 2.9 to 4.6 times less.
- **The packed bytes cost little at startup.** The packed script's gap was 25 / 33 / 32 ms larger than C's, while it carries all 11.6 MB of the app's server code and C carries 1.8 MB. That is about 17 to 22 ms per MB of script, close to the transport spike's 15 to 26 ms per MB for wrapped code that never runs. Per MB of source code packed, about 4 times less (derived from the 0.27 gzip + base64 ratio).
- **Unpacking is where packed loses on a route that needs large lazy parts.** Packed `/code` was 67 / 67 / 109 ms slower than C to first byte. Its handler was 43 / 84 / 68 ms slower, and unpacking accounted for 55 / 90 / 79 ms of it, more than half of that in the wasm part.
- **Against the transport spike's split through the pull zone** (different run, so derived across runs): A on CDN hits was 113 ms slower than C in New York, 42 ms slower in Frankfurt and 37 ms faster in Singapore, and on CDN misses 133 to 1,006 ms slower. Packed was 67 to 109 ms slower than C here, with no fetch and so no miss tail.

## What it decides

- **Packing works on bunny.net.** `DecompressionStream('gzip')` exists, the whole 11.6 MB app fits in a 3.36 MB script that starts, and every route renders without a network fetch. As plain functions the same app never starts (transport spike).
- **The cost model is bytes of parse work plus unpacking on first use, not script bytes.** A packed string costs about as much at startup as never-run wrapped code of the same size, and packs about 3.7 times as much code into it. So the size budget of option 7 (`options-split`) is better spent on packed strings than on functions for anything not needed at startup.
- **The price is per route, not per site.** A route pays the unpacking of the lazy parts it imports, here 55 to 90 ms for 1.1 MB of `/code` parts, on every cold request. `/` paid 6 to 7 ms. That is cheaper than one fetch round on a CDN miss and comparable to the split's cost on CDN hits.
- **Recommendation:** pack lazy parts in the script by default, with the eager part as functions, and keep fetched parts only for what does not fit (option 7 with option 6's encoding). For this app that means nothing is fetched. Two refinements are expected to cut the unpacking cost and were not measured: a faster base64 decode than `atob` plus `Uint8Array.from` (for example `Uint8Array.fromBase64`, not checked on bunny.net), and keeping parts that are already compressed data, like Shiki's base64 wasm, uncompressed or as functions.

## Not covered

- More than 4 to 7 cold samples per cell. The New York functions row is bimodal (361 to 381 and 584 to 670 ms), and Frankfurt C here (470 ms) was slower than in the transport spike (356 ms), so compare within this run.
- Where the packed script stops starting. Expected near the 7 MB script limit, about 25 MB of source at this ratio; not measured.
- A JavaScript inflate fallback, since `DecompressionStream` worked.
- Memory: the isolate keeps the packed strings and every unpacked module for its lifetime.
- Other routes, other apps, middleware scripts, and code that runs at startup rather than on first import.
